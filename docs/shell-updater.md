# Updater of the Rust shell

The Rust shell (`crates/noct-app`) has its updater configured. The shell carries `tauri-plugin-updater`, pinned at
2.14.1, and registers it at start, because the configuration is complete (`crates/noct-app/src/updater.rs`).
Registering the plugin makes no request for an update. Nothing calls its check, download or install commands, and
the main window is granted no updater permission, so the shell cannot check for, download or install an update yet.
Activating the updater is a separate change, described under [Activation](#activation).

The current Electron application keeps its own updater (`electron/updates`, `docs/updates.md`). The two are not
connected: the shell's configuration does not read the Electron release metadata.

document.

To check that a `.pub` file is the registered key:

```sh
base64 -d < noct-updater.key.pub | head -n 1
# untrusted comment: minisign public key: 40503B624D87D646
test "$(cat noct-updater.key.pub)" = "$(node -p "require('./crates/noct-app/tauri.conf.json').plugins.updater.pubkey")"
```

## Configuration

```json
"plugins": {
  "updater": {
    "pubkey": "dW50cnVzdGVkIGNvbW1lbnQ6IG1pbmlzaWduIHB1YmxpYyBrZXk6IDQwNTAzQjYyNEQ4N0Q2NDYKUldSRzFvZE5ZanRRUU54c3A1UHRkUG1yNE5nL3Q5cm9IMHJONjBIVVRZRGZDNVZXMVNaRFJxQncK",
    "endpoints": ["https://github.com/gustavomfg/NOCT/releases/latest/download/latest.json"],
    "requireSignedVersion": true
  }
}
```

- **`pubkey`** is required by the plugin, and every download is verified against it. Verification cannot be turned
  off: the plugin has no option for that.
- **`endpoints`** lists one HTTPS endpoint, the manifest of the latest release. The plugin refuses a non-HTTPS
  endpoint unless `dangerousInsecureTransportProtocol` is set, and it is not set.
- **`requireSignedVersion`: true** makes the updater accept an update only when its signature names the version the
  manifest announces. Without it, a manifest that is not signed could pair a newer version number with the URL and
  signature of an older, validly signed release, and force a downgrade. The field is `require_signed_version` in the
  plugin's configuration (`src/config.rs`) in tauri-plugin-updater 2.12.0 and 2.14.1, both checked in their sources.
  It needs signatures that carry the version: the Tauri CLI writes that version when it signs with `--app-version`,
  and the release workflow passes that flag.
- **No other key.** `dangerousInsecureTransportProtocol`, `dangerousAcceptInvalidCerts`,
  `dangerousAcceptInvalidHostnames` and `allowDowngrades` are absent, so each keeps its default (`false`). The plugin
  ignores unknown keys without an error, so a misspelled option would have no effect and no warning. The test lists
  the exact keys instead.

Tauri 2.12.5 is the version the shell uses. The plugin is pinned at `=2.14.1` in the workspace `Cargo.toml`, and that
release requires `tauri` 2.12 (its `Cargo.toml`), the line of this shell. Only the pinned version is supported: the
release that first added `require_signed_version` was not checked, so no older plugin is claimed to honour it.

## What is checked

The configuration is locked by `crates/noct-app/tests/updater_config.rs`, which runs in `cargo test -p noct-app`:

- the configured public key is the registered one;
- the one endpoint is the release endpoint, over HTTPS;
- `requireSignedVersion` is `true`;
- the keys under `plugins.updater` are exactly `endpoints`, `pubkey` and `requireSignedVersion`;
- the plugin is named, and its commands are called, only in `src/updater.rs`
  (`the_plugin_is_registered_and_called_only_by_the_updater_module`).

The test that an insecure flag fails was checked by hand: adding `dangerousInsecureTransportProtocol` makes
`the_updater_has_no_other_option` fail.

`crates/noct-app/tests/capabilities.rs` compares the permissions of the main window with the full list it grants.
That list has no updater permission, so the window cannot call the plugin's commands, although the plugin is
registered at start.

What this does not show: no CI job opens a window, so the configuration is not loaded by a running window here. The
plugin's setup stores its configuration and makes no request (checked in the 2.14.1 source). It does not decode the
public key or contact the endpoint at start: the key is decoded only when an update is verified, and no code does that
yet.

## Activation

The plugin dependency and its registration are in place (`004dba3`, `crates/noct-app/src/updater.rs`). Checking for
and installing an update needs, in one reviewed change:

1. an updater permission granted to the main window, with the capability test changed to match;
2. a release that can be installed and updated from, which means the release workflow has published one for a
   `rust-v` tag (see [Release workflow](#release-workflow)).

Until step 1 is done, the window cannot reach the plugin, and the shell makes no request for an update.

## Key rotation

Installed copies of the shell trust only the public key compiled into them. Changing the key in the configuration
alone would therefore make every installed copy reject the next update. A rotation is a bridge release, signed with
the old key, that carries the new public key; only the releases after it are signed with the new key.

Rotate on a trusted machine, not in CI and not in this repository. Routine rotation needs the old private key, which
must still be held and unexposed.

1. Generate the new key pair interactively, so that the password is not written in the shell history, and keep the
   files outside the repository:

   ```sh
   cargo tauri signer generate -w "$HOME/secure/noct-updater-next.key"
   ```

   Read the new key id from the first line of the `.pub` file, and the base64 value of that file.

2. Open a release PR that changes `plugins.updater.pubkey` to the new value, and the table in this document to the
   new key id and the SHA-256 of the new value. The bridge release is the first `v*` tag of that PR. The release
   workflow signs it with the **old** key, which is still held in the `release` environment.
3. The release workflow checks every signature against the key in the configuration. In the bridge release that is
   the new key, while the signature is made with the old one, so the check stops the release. This is intended, and
   the bridge therefore needs a reviewed change to that check: it verifies the bridge against the old public key for
   that one tag. The change is part of the release PR and is removed in the next one. The bridge is not automated.
4. Once the bridge release is published and an installed copy has taken it, replace the two secrets in the
   `release` environment with the new private key and its password. Keep the old private key only until that
   replacement is verified, then destroy it.
5. Confirm with the next release that its signatures verify with the new key.

If the old private key may have been exposed, do not bridge with it: anyone holding it could sign a bridge release.
Stop publishing updates, remove the old secrets, and tell users to reinstall the shell from a source they trust.
Record the incident in this document, with the key ids and the dates.
