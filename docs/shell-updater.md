# Updater of the Rust shell

The Rust shell (`crates/noct-app`) has its updater configured. The shell carries `tauri-plugin-updater`, pinned at
2.14.1, and registers it at start, because the configuration is complete (`crates/noct-app/src/updater.rs`).
Registering the plugin makes no request for an update. Nothing calls its check, download or install commands, and
the main window is granted no updater permission, so the shell cannot check for, download or install an update yet.
Activating the updater is a separate change, described under [Activation](#activation).

The current Electron application keeps its own updater (`electron/updates`, `docs/updates.md`). The two are not
connected: the shell's configuration does not read the Electron release metadata.

The public key is not a secret, and the file is committed. The private key never goes into the repository, the
configuration, a log or a document. `tests/updater_config.rs` fails if the file and the configuration differ.

To check that the committed file is the registered key:

```sh
base64 -d < docs/noct-updater.key.pub | head -n 1
# untrusted comment: minisign public key: 40503B624D87D646
test "$(cat docs/noct-updater.key.pub)" = "$(node -p "require('./crates/noct-app/tauri.conf.json').plugins.updater.pubkey")"
```

## Configuration

```json
"plugins": {
  "updater": {
    "pubkey": "dW50cnVzdGVkIGNvbW1lbnQ6IG1pbmlzaWduIHB1YmxpYyBrZXk6IDQwNTAzQjYyNEQ4N0Q2NDYKUldSRzFvZE5ZanRRUU54c3A1UHRkUG1yNE5nL3Q5cm9IMHJONjBIVVRZRGZDNVZXMVNaRFJxQncK",
    "endpoints": ["https://github.com/gustavomfg/NOCT/releases/latest/download/latest.json"],
    "requireSignedVersion": true
  }
}
```

- **`pubkey`** is required by the plugin, and every download is verified against it. Verification cannot be turned
  off: the plugin has no option for that.
- **`endpoints`** lists one HTTPS endpoint: `https://github.com/gustavomfg/NOCT/releases/download/updater-feed/latest.json`,
  the manifest of the `updater-feed` channel. That channel is a pre-release that the release workflow moves; it is not
  the release marked latest, which the Electron application reads. The plugin refuses a non-HTTPS endpoint unless
  `dangerousInsecureTransportProtocol` is set, and it is not set.
- **`requireSignedVersion`: true** makes the updater accept an update only when its signature names the version the
  manifest announces. Without it, a manifest that is not signed could pair a newer version number with the URL and
  signature of an older, validly signed release, and force a downgrade. The field is `require_signed_version` in the
  plugin's configuration (`src/config.rs`) in tauri-plugin-updater 2.12.0 and 2.14.1, both checked in their sources.
  It needs signatures that carry the version: the Tauri CLI writes that version when it signs with `--app-version`,
  and the release workflow passes that flag.
- **No other key.** `dangerousInsecureTransportProtocol`, `dangerousAcceptInvalidCerts`,
  `dangerousAcceptInvalidHostnames` and `allowDowngrades` are absent, so each keeps its default (`false`). The plugin
  ignores unknown keys without an error, so a misspelled option would have no effect and no warning. The test lists
  the exact keys instead.

Tauri 2.12.5 is the version the shell uses. The plugin is pinned at `=2.14.1` in the workspace `Cargo.toml`, and that
release requires `tauri` 2.12 (its `Cargo.toml`), the line of this shell. Only the pinned version is supported: the
release that first added `require_signed_version` was not checked, so no older plugin is claimed to honour it.

## What is checked

The configuration is locked by `crates/noct-app/tests/updater_config.rs`, which runs in `cargo test -p noct-app`:

- the configured public key is the registered one;
- the one endpoint is the `updater-feed` channel, over HTTPS, and never the release marked latest;
- `requireSignedVersion` is `true`;
- the keys under `plugins.updater` are exactly `endpoints`, `pubkey` and `requireSignedVersion`;
- the plugin is named, and its commands are called, only in `src/updater.rs`
  (`the_plugin_is_registered_and_called_only_by_the_updater_module`).

The test that an insecure flag fails was checked by hand: adding `dangerousInsecureTransportProtocol` makes
`the_updater_has_no_other_option` fail.

`crates/noct-app/tests/capabilities.rs` compares the permissions of the main window with the full list it grants.
That list has no updater permission, so the window cannot call the plugin's commands, although the plugin is
registered at start.

What this does not show: no CI job opens a window, so the configuration is not loaded by a running window here. The
plugin's setup stores its configuration and makes no request (checked in the 2.14.1 source). It does not decode the
public key or contact the endpoint at start: the key is decoded only when an update is verified, and no code does that
yet.

## Activation

The plugin dependency and its registration are in place (`004dba3`, `crates/noct-app/src/updater.rs`). Checking for
and installing an update needs, in one reviewed change:

1. an updater permission granted to the main window, with the capability test changed to match;
2. a release that can be installed and updated from, which means the release workflow has published one for a
   `rust-v` tag (see [Release workflow](#release-workflow)).

Until step 1 is done, the window cannot reach the plugin, and the shell makes no request for an update.

## Release workflow

`.github/workflows/shell-release.yml` builds, signs and publishes the shell's updater artifacts. It is written and has
not run. Its only trigger is a `rust-v*` tag, and nothing in this change pushes one. A `rust-v` tag starts no Electron
workflow: `stable-release.yml` matches `v[0-9]*` and `package-validation.yml` matches `v*`, and
`scripts/shell-release.test.mjs` checks that neither pattern matches a shell tag.

| Job | Runs on | Secrets | What it does |
| --- | --- | --- | --- |
| `gate` | Linux | none | Requires a stable `rust-vX.Y.Z` tag that names a commit of this repository. The version must match `crates/noct-app/tauri.conf.json` and the workspace `Cargo.toml`. The release notes `docs/releases/rust-vX.Y.Z.md` must exist. No release may exist for the tag. A successful `rust-shell-validation.yml` run for the tagged commit must exist. The gate does not look at `main`. |
| `build` | Linux x86_64 (AppImage), Windows x86_64 (NSIS), macOS arm64 (`.app.tar.gz`) | none | `cargo tauri build --no-sign` with `createUpdaterArtifacts` for this build only. Uploads the one updater artifact of each platform, unsigned. |
| `sign` | Linux, `release` environment | `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Signs each artifact with `cargo tauri signer sign --app-version`, which binds the version into the signature. Verifies each signature with minisign against `plugins.updater.pubkey` in the configuration. Writes `latest.json` with `scripts/shell-latest-json.mjs`, which refuses a signature that names another file or version. |
| `publish` | Linux | none | Attests the release assets with `actions/attest-build-provenance`. Creates the release of the exact tag as a **pre-release, never the latest**, with the signed artifacts and without `latest.json`. Then moves the `updater-feed` pre-release to the new `latest.json` (created the first time, then replaced with `--clobber`), and refuses a version older than the one the feed holds. Afterwards it checks that the feed serves the signed manifest, and that the release is a pre-release and not the latest. The job runs one at a time, because the feed is shared. |

The release channels, and what each one is for:

- **`rust-vX.Y.Z`** (one per release): the signed artifacts. A pre-release. Nothing reads it except the manifest's URLs.
- **`updater-feed`** (one, permanent): the pre-release whose only asset is `latest.json`. The shell's endpoint points here,
  so the endpoint never changes with the version.
- **`vX.Y.Z`** (the Electron application): unchanged. It is the release marked latest, which the Electron updater reads.
  The release workflow never marks a shell release latest, and `scripts/shell-release.test.mjs` fails if it does.

Every action is pinned to a commit SHA. The attestation action is the one the build provenance dry run verified, at the
same pin. The workflow tests (`scripts/shell-release.test.mjs`) lock the trigger, the permissions, the pins, the one job
that reads the secrets, the signing order, the tag the gate and the publish job compare, and the job that publishes.
`scripts/shell-latest-json.test.mjs` covers the manifest builder, which refuses any tag that is not `rust-v` plus the version.

Before the first tag, the maintainer must:

1. Create the `release` environment in the repository settings, with the two secrets, and limit its deployments to
   `rust-v*` tags. This change does not create them, and no key is generated here.
2. Decide who holds the private key. This is still open: ADR 0001, open decision 1.

Do not push a `rust-v*` tag until these blockers are resolved:

- **The `latest` release is shared with the Electron application: resolved by the channel.** The Electron updater reads
  `releases/latest` for the tag, then `latest.yml` from that release
  (`node_modules/electron-updater/out/providers/GitHubProvider.js`, `getLatestTagName`). A shell release is a pre-release,
  so it never takes that mark, and the shell reads its own channel, `updater-feed`. What stays a rule and not a
  mechanism: nobody marks a shell release as latest by hand, and the publish job's check would catch it only on that
  run.
- The **updater cannot be used yet**: the window has no updater permission (see [Activation](#activation)). A release
  can be produced now, but no shell can check for or install it until that step is done.
- The workflow publishes the updater artifacts to a pre-release and the manifest to `updater-feed`. Installers for users
  (DMG, MSI) are not part of it yet.

What is not verified: nothing here has run. CI has not built a shell bundle with `createUpdaterArtifacts`, so the
artifact names, the AppImage tooling on a hosted runner, the NSIS and macOS bundles, and the minisign check of a
Tauri signature are all unconfirmed until the first real run. A run publishes a real release, so first test the
workflow in a copy of the repository (a fork with its own `release` environment), not in the public one. The gate's
query for the shell CI run of the tagged commit has not run against GitHub. Nor has the feed: that a pre-release
download URL serves the feed's asset, and that `releases/latest` skips the shell's pre-releases, are the GitHub behaviour
the design relies on, and no run has observed them. `actionlint` 1.7.12, the version `package-validation.yml` uses, is run
locally with shellcheck on `PATH`, as CI runs it. Without shellcheck, actionlint skips the shell in `run:` steps, and a CI
run of this branch failed on a shellcheck finding (SC2016) that a local run without shellcheck had not shown. That job runs
on pull requests, on pushes to `main` and on `v*` tags. A push to `migration/rust` with no open pull request is not linted.

## Key rotation

Installed copies of the shell trust only the public key compiled into them. Changing the key in the configuration
alone would therefore make every installed copy reject the next update. A rotation is a bridge release, signed with
the old key, that carries the new public key; only the releases after it are signed with the new key.

Rotate on a trusted machine, not in CI and not in this repository. Routine rotation needs the old private key, which
must still be held and unexposed.

1. Generate the new key pair interactively, so that the password is not written in the shell history, and keep the
   files outside the repository:

   ```sh
   cargo tauri signer generate -w "$HOME/secure/noct-updater-next.key"
   ```

   The public key is written next to it, at the same path with `.pub` appended. Read the new key id from its first
   line, and use the base64 value of that file as the new `pubkey`.

2. Open a release PR that changes `plugins.updater.pubkey` to the new value, and the table in this document to the
   new key id and the SHA-256 of the new value. The bridge release is the first `rust-v*` tag of that PR. The release
   workflow signs it with the **old** key, which is still held in the `release` environment.
3. The release workflow checks every signature against the key in the configuration. In the bridge release that is
   the new key, while the signature is made with the old one, so the check stops the release. This is intended, and
   the bridge therefore needs a reviewed change to that check: it verifies the bridge against the old public key for
   that one tag. The change is part of the release PR and is removed in the next one. The bridge is not automated.
4. Once the bridge release is published and an installed copy has taken it, replace the two secrets in the
   `release` environment with the new private key and its password. Keep the old private key only until that
   replacement is verified, then destroy it.
5. Confirm with the next release that its signatures verify with the new key.

If the old private key may have been exposed, do not bridge with it: anyone holding it could sign a bridge release.
Stop publishing updates, remove the old secrets, and tell users to reinstall the shell from a source they trust.
Record the incident in this document, with the key ids and the dates.
